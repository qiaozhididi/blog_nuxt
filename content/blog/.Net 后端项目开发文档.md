# .NET 后端项目开发文档

本系统是面向鞋业制造企业的大型 ERP/MES 后端，基于 **.NET 8** 提供 REST API，覆盖研发、BOM、采购代工、生产执行、质量、仓储、人事、财务、工作流审批等 20+ 业务域，全仓库 9300+ 个源码文件。系统以 Docker 容器部署于华为云，支持**一套代码多工厂差异化部署**。

## 技术栈

| 分类 | 技术选型 | 说明 |
| -- | -- | -- |
| 运行时 | .NET 8（C# 12） | LTS 版本，启用 Nullable + ImplicitUsings |
| Web 框架 | ASP.NET Core Web API | REST API 宿主 |
| ORM / 数据库 | EF Core 8 + SQL Server | 内部扩展方法统一注册 |
| 内部框架 | 自研核心框架（私有 NuGet 包） | 私有 NuGet 分发，提供 DbContext/Controller 基类、统一返回体 `R<T>`、UserToken、MQ 消费基类 |
| 消息队列 | RabbitMQ + EasyNetQ 7.8 | 跨模块事件驱动，含死信队列 |
| 进程内事件 | MediatR | 领域事件通知（INotificationHandler） |
| 定时任务 | Quartz.NET | Conch Job 封装（IHostedService 托管） |
| 对象映射 | AutoMapper | 程序集扫描自动注册 Profile |

## 项目结构

单解决方案共 11 个项目，采用**纵向分层 + 横向按业务域分包**：

| 层 | 职责 |
| -- | -- |
| Web 层 | 启动入口、Controllers（按业务域分包）、Swagger 分组、定时任务、Excel 模板文件 |
| 业务逻辑层 | 业务服务接口与实现（接口 + Impl 目录分离）、MQ 事件（Consumer / Publisher / Payload）、MediatR 进程内事件处理器、BaseService 基类 |
| 数据访问层 | EF Core DbContext（partial class 按业务域拆分）、泛型仓储 |
| 实体层 | 数据库实体（按业务域分包） |
| 视图对象层 | 接口出入参（Param / View 成对）与 AutoMapper Profile |
| 传输对象层 | 层间、服务间数据传输对象 |
| 枚举层 | 枚举集中管理（订单状态、BOM 操作类型等） |
| 公共层 | 常量、工具类、Excel 帮助类、resx 国际化资源 |
| 通用异常 | BusinessException、ErrorCode |
| 遗留 ORM | 早期 XML 配置式 SQL 组件（强签名），历史模块在用 |
| 测试 | Controller / Service 两个测试工程 |

## 架构设计

### 请求调用链

```text
HTTP 请求（Lang 请求头 → 国际化中间件）
   ↓
Controller（继承框架 Controller 基类，Route("api/模块/资源/")）
   ↓
Service 接口（IXxxService）→ 实现类（Impl 目录，约定式自动注册）
   ├─ EF Core（主 DbContext）→ SQL Server
   ├─ MediatR.Publish → 进程内 NotificationHandler（如库存入库后更新台账）
   ├─ EasyNetQ Publish → RabbitMQ（BOM 变更 / MRP / 订单事件 → 下游消费者）
   └─ AutoMapper → Vo，统一包装 R<T> 返回
```

### 依赖注入

- **约定式自动注册**：通过扩展方法扫描程序集中所有继承 Service 基类的实现类自动注册，避免 1400+ 个 Service 手写注册。
- **AutoMapper 扫描**：`AddAutoMapper` 传入解决方案内全部业务程序集，自动收集所有 Profile。
- **生命周期**：DbContext 与业务服务为 Scoped；MQ Consumer 为 Singleton，消费时通过 `IServiceProvider.CreateScope()` 开新作用域，规避单例捕获 Scoped 服务的问题。
- **BaseService 基类**：统一注入 `IMapper`、`IStringLocalizer<Resource>`、`UserToken`（当前登录用户上下文），新增业务 Service 只需接口 + 实现两个文件。

### 数据访问

- 主 DbContext 继承内部框架的基类（封装审计字段、软删除、HierarchyId/空间类型等横切逻辑），因承载 2000+ 实体，使用 **partial class 按业务域拆分为 57 个文件**，每个文件只声明本域的 `DbSet<T>` 与 FluentAPI 配置，降低合并冲突。
- 项目内两种风格并存：少数场景使用泛型仓储 `IRepository<T>` 封装领域级查询；多数 Service 直接注入 DbContext 使用 LINQ，配合 `PredicateBuilder` 动态条件与动态 SQL 扩展。EF Core 的 DbContext 本身即 Unit of Work，仓储层按需引入而非强制。

### 消息与异步

事件分两个层次，边界清晰：

| 维度 | MediatR（进程内） | RabbitMQ / EasyNetQ（进程外） |
| -- | -- | -- |
| 作用 | 模块内解耦，与主流程同一事务边界 | 跨模块/跨系统通知，最终一致性 |
| 典型场景 | 入库后更新台账、出库写备注 | BOM 变更通知、MRP 触发、缓存失效广播 |
| 可靠性 | 随请求成败 | 消息持久化 + 死信队列 |

MQ 封装在业务逻辑层的事件模块中，按 Payload（消息体）、Publisher（发布服务）、Consumer（消费者）三类组织：Consumer 继承框架基类 `MQConsumerBaseImpl<TMessage>`，只需声明 RoutingKey、QueueName、死信队列和 Handler 列表；Exchange/Queue 命名集中在常量类统一管理。Consumer 负责收消息、Handler 负责业务，职责分离。

### 定时任务

基于 Quartz.NET 封装了 Conch Job 框架：`ConchJobSchedule` 抽象 Job 定义与 Cron 配置并注册进 DI，`ConchJobFactory` 让 Quartz 从 DI 容器创建 Job 实例，`ConchJobHostService`（IHostedService）随应用启动装配所有任务。业务 Job 多为「周期巡检 + 飞书/邮件异常通知」模式，如模具异常巡检、借出超期检查、测试数据清理。

### 国际化

标准本地化中间件 + resx 资源文件（zh-Hans / en-US 双套，强类型生成器，集中在公共层的 Locales 目录）。自定义 `CustomRequestCultureProvider` 从 **`Lang` 请求头**读取语言（非 en-US 回退 zh-CN）——前端语言是应用内设置而非浏览器设置，显式 Header 比 Accept-Language 更可控，也便于 App/小程序统一行为。错误码与文案分离（I18NErrorCode + 按业务域的 I18N 文案类）。

### API 文档

Swagger 按业务域分组：分组枚举搭配自定义 `GroupInfoAttribute` 声明元数据，`AddSwaggerGen` 通过反射自动为每组生成文档，仅在 Development / local 环境开启。

## 关键选型说明

**为什么是 .NET 8 / C#**：公司技术栈以 .NET 为主，内部框架与遗留 ORM 均为 .NET 生态，迁移成本远高于收益；.NET 8 为 LTS 版本，性能与容器化支持成熟；制造业大量单据报表场景（Excel/PDF/条码）在 .NET 生态有 NPOI、itext7、QRCoder/ZXing 等成熟方案。

**为什么是单体分层而非微服务**：ERP/MES 的核心痛点是跨模块强一致性（BOM 变更联动 MRP、订单、库存），微服务化的分布式事务成本极高；系统按工厂私有化部署，无互联网级弹性扩缩容需求。模块间已通过 RabbitMQ 事件解耦，未来可按事件边界拆分。

**为什么用 Newtonsoft.Json 而非 System.Text.Json**：一行配置全局统一时间格式（`yyyy-MM-dd HH:mm:ss`）；自定义 `G3JsonLongConverter` 将 long 主键序列化为字符串，解决 JS Number 精度丢失；存量代码大量依赖 Newtonsoft 行为。MQ 序列化（EasyNetQ）则选用了 System.Text.Json——新链路用新栈，存量不动的渐进策略。

**多工厂差异化**：一套代码 + 配置开关。启动时读入全局上下文 `Global`：`FactoryCode`（工厂编码）、`ERPType`（对接 ERP 类型）、`IsSoleFactory`（独底厂）、`IsBudget`（预算）等约 10 个开关控制业务分支。该模式简单直接，但开关组合随工厂数增长存在复杂度风险，后续可演进为特性开关 + 策略模式。

**Vo 与 Dto 分离**：Vo 面向接口出入参（Param/View 成对，服务前端契约），Dto 面向层间/服务间传输（导入比对、跨模块数据拼接）。分项目存放使 Vo 可引用 AutoMapper Profile 而不污染 Dto。

## 部署与配置

- **Docker**：基于华为云 SWR 私有定制镜像（预装 SkiaSharp 等 native 依赖的 aspnet:8.0），拷贝发布产物，入口为 Web 层主程序集，暴露 80 端口。
- **私有 NuGet**：指向内网私有源，分发自研核心框架包（版本号规则：年月 + 迭代 + 客户代号）。
- **多环境配置**：按环境区分的 appsettings 配置文件，涵盖连接串、Redis、RabbitMQ、飞书 AppId/Secret、Azure Blob、文件管理服务；通过 PathBase 支持网关路径前缀。
- **本地打印**：仓库配套本地标签打印控制器程序，解决工厂车间浏览器无法直连打印机的场景。

## 测试

解决方案下含 Controller 与 Service 两个测试工程：xUnit + Moq + `Xunit.DependencyInjection`（测试复用真实 DI 容器）+ coverlet 覆盖率；`EFCore.TestSupport` 提供 InMemory/SQLite 替身，Service 层测试不依赖真实 SQL Server。覆盖重点为核心计算逻辑（MRP、鞋型计划），大量 CRUD 依赖联调与工厂验收。
